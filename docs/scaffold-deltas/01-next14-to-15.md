# Scaffold delta 01 — Next.js 14 → 15

> **Source of truth:** Andy's Full Project Kickoff Brief (2026-04-09 15:43 BST).
> **Trigger:** Brief specifies Next.js 15 (App Router, Server Components, Server Actions). Current scaffold is pinned to Next 14.
> **Status:** Design doc, not yet applied. Blocked on Andy's approval of `docs/training-data-plan.md`.

## Why this matters

Next.js 15 is not a cosmetic upgrade from 14. Three concrete things change for us:

1. **Caching defaults flipped.** In 14, `fetch()` and route handlers were aggressively cached by default. In 15, both are **uncached** by default — you opt into caching explicitly. This is load-bearing for the CEF wizard because CEF autosave hits `POST /api/admissions/cef/[step]` dozens of times per step, and 14's default would have silently cached those mutations. The 15 default is the correct default for us.

2. **Request-scoped async APIs.** `cookies()`, `headers()`, `draftMode()`, and `params` / `searchParams` in route handlers are now **async**. Any code calling them has to `await`. We have ~8 call sites in the current scaffold that would otherwise silently return stale references.

3. **React 19.** Next 15 ships with React 19 by default. `useFormState` is renamed to `useActionState`, `useFormStatus` behaviour changes slightly, and `ref` can now be a prop (no more `forwardRef` for leaf components). This matches Andy's Server Actions requirement cleanly.

## What changes mechanically

### Package versions

Current `package.json`:
```json
{
  "dependencies": {
    "next": "14.2.x",
    "react": "18.3.x",
    "react-dom": "18.3.x"
  }
}
```

Target:
```json
{
  "dependencies": {
    "next": "15.0.x",
    "react": "19.0.x",
    "react-dom": "19.0.x"
  }
}
```

Pin to the latest stable 15.0.x at the time of apply — not `^15` and not `*`. We want the upgrade to be reproducible.

### Automatic codemod

Run the official Next codemod first to catch the mechanical 90%:

```bash
npx @next/codemod@canary upgrade latest
```

This handles: the async `cookies()`/`headers()`/`params` migration, the `NextRequest`/`NextResponse` import path changes, and a handful of `next.config.mjs` option renames.

### Manual follow-ups the codemod misses

1. **`middleware.ts`** — the codemod leaves our custom `namespaceFor()` helper alone, but the request-id header extraction changes from a synchronous `req.headers.get()` to remaining sync (it's still a `Headers` instance, not a promise). Nothing to do here. **Test:** the existing `tests/lib/middleware-namespace.test.ts` should still pass as-is.

2. **`app/(admissions)/layout.tsx`** — currently awaits `getCurrentUser()`, which internally reads cookies. The cookie read inside `getCurrentUser` needs to become `await cookies()`. The call site in the layout doesn't change — only the internals of `lib/auth/server.ts`.

3. **`lib/api/instrumented-route.ts`** — the HOF wraps route handlers. In 15, route handler signatures for dynamic routes receive `params` as a `Promise<{...}>`. We need to handle both (for backwards compatibility during the transition) or commit to 15-only. **Decision:** 15-only. Drop the shim.

4. **CSRF token handling in `lib/security/csrf.ts`** — reads cookies via `cookies()`. Becomes `await cookies()`. Tests don't change because they stub the cookies store directly.

5. **`app/error.tsx`** and `app/(admissions)/error.tsx` and `app/(wellbeing)/error.tsx` — no API changes but worth re-verifying that `reset()` still behaves the same way with React 19's error boundaries. Should just work.

6. **`useFormState` → `useActionState`** — we don't have any Server Action forms yet in the scaffold (the signin form is a fetch `onSubmit`), but the codemod will rename any latent references. **Test:** `pnpm typecheck` after the rename is the canary.

### CI changes

- `.github/workflows/ci.yml` — bump the Node version matrix to `20.x` and `22.x`. Drop `18.x` — Next 15 requires Node ≥ 18.18 and we don't need the older row.
- The `banned-providers` grep job doesn't change.
- The `cross-surface-imports` grep job doesn't change.
- Add a new one-liner grep to the lint job: `grep -R "useFormState" app/ lib/ components/` should return zero. If it returns anything, we missed a codemod.

### Risk and rollback

**Risk is low.** The 14 → 15 upgrade is less disruptive than 13 → 14 was. The main thing that bites people is forgetting to `await` cookies/headers, which is a typescript error, not a runtime bug.

**Rollback plan:** one git revert of the upgrade PR. The lockfile goes back. We lose nothing because none of the subsequent scaffold deltas or training-data work depends on 15-specific features yet.

## PR sequence

One PR, one commit per step:

1. `feat(next15): bump next to 15.0.x and react to 19.0.x`
2. `chore(next15): run @next/codemod automatic migrations`
3. `fix(next15): await cookies() in auth + csrf layers`
4. `fix(next15): drop backwards-compat params shim in instrumented-route`
5. `chore(next15): bump node matrix in CI to 20/22`
6. `test(next15): verify full vitest + typecheck pass`

Total: ~1 hour of focused work, assuming zero test failures.

## Definition of done

- `pnpm install` clean
- `pnpm typecheck` zero errors
- `pnpm test` zero failures
- `pnpm build` succeeds with no 15-deprecation warnings in the build log
- Manual smoke: `pnpm dev`, open `/signin`, `/cef/1`, `/dashboard`, `/adie`, `/counsellor` — every page renders, every header / nav interaction works, autosave footer on CEF step pings the API without a 500
- CI green on the PR before merge

## Out of scope for this delta

- **Turbopack** — Next 15 stabilises Turbopack for `dev`. We do **not** switch to it yet. Stick with Webpack dev for M1 to reduce surface area for bugs. Revisit in M3.
- **`cacheLife` / `cacheTag` / `use cache`** — Next 15's new caching primitives are opt-in and not needed for the CEF flow. Park for Phase 2 when we start caching school-lookup results.
- **Partial Prerendering** — experimental. Do not enable. PPR is a rabbit hole and we don't need it for MVP.
